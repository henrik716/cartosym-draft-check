CartoSym 2.0 draft: judgement calls, rendered

Where the spec text does not settle how a renderer should behave, the draft requirements in PR #133 make a choice. Each card renders the same small map with the draft's choice and the alternatives. Because the draft renderer implements the draft itself, it can show what each choice looks like, but not whether that choice is the intended one: that is for the SWG to decide. Comparing with an independent renderer shows whether others read the requirements the same way, so each card links its style, data and view settings (all in kit.zip), and the playground lets you edit a style and see the result.

Part 1: vector styling

Symbolizer opacity: whole symbol or each part#

What the draft says
/req/core/opacity
  • An Encoding SHALL support defining an opacity Symbolizer property as a float between 0 (fully transparent) and 1 (fully opaque).
  • A Renderer SHALL support portraying a feature or coverage cell with the opacity specified by the resolved opacity property, applied to the portrayal as a whole.

With opacity: 0.5, is the symbol made translucent as a whole, or are fill and stroke made translucent separately? Separately, the stroke and fill overlap shows through.

Style (CartoSym-JSON)Edit in playground
{
  "stylingRules": [
    {
      "selector": {
        "op": "=",
        "args": [
          {
            "sysId": "dataLayer.id"
          },
          "Background"
        ]
      },
      "symbolizer": {
        "fill": {
          "color": [46, 134, 222]
        },
        "stroke": {
          "width": {
            "px": 0
          }
        }
      }
    },
    {
      "selector": {
        "op": "=",
        "args": [
          {
            "sysId": "dataLayer.id"
          },
          "Parcels"
        ]
      },
      "symbolizer": {
        "opacity": 0.5,
        "fill": {
          "color": [243, 156, 18]
        },
        "stroke": {
          "color": [110, 44, 0],
          "width": {
            "px": 14
          }
        }
      }
    }
  ]
}

The draft says the opacity applies to the portrayal as a whole, as SVG and CSS group opacity do. Applied to fill and stroke separately, the overlap shows through.

Casing beneath or above the stroke#

What the draft says
/req/casing/casing
  • An Encoding SHALL support defining a casing Stroke property as a StrokeStyling object.
  • A Renderer SHALL support drawing the casing of a stroke along the same geometry as the stroke, using the StrokeStyling specified by the casing property, beneath the main stroke.
/req/casing/center
  • An Encoding SHALL support defining a center Stroke property as a StrokeStyling object.
  • A Renderer SHALL support drawing the center line of a stroke along the same geometry as the stroke, using the StrokeStyling specified by the center property, on top of the main stroke.

A road with a 14 px yellow stroke, a 22 px red casing at 60 % opacity (so what lies under it shows through) and a thin white centre line. Is the casing drawn beneath the stroke (an outline) or on top of it?

The default marker#

What the draft says
/req/core/default-values
  • An Encoding SHALL support omitting Symbolizer properties and object members for which a default value is defined in this section.
  • A Renderer SHALL support using the default values defined in this section for Symbolizer properties and object members which are not set by any selected StylingRule.
/req/vector/marker
  • An Encoding SHALL support defining a marker Symbolizer property as an array of graphical elements (Graphics).
  • A Renderer SHALL support drawing the graphical elements of a marker at the points of vector geometry (for points and line strings) and at the centroid of polygons.
/req/vector/dot
  • An Encoding SHALL support defining a Dot Graphic inheriting from a base Shape class specifying a stroke, from which the color and the size of the point is inferred.
  • A Renderer SHALL support drawing the Graphics as a round dot using the width of its Stroke as the point size and in the color of the Stroke.

A style that sets only a fill and a stroke, and no marker. Clause 7's defaults say the default Marker is a single default Dot (white, 10 px), and markers are drawn at points, line vertices and polygon centroids. Does every feature get a white dot?

Style (CartoSym-JSON)Edit in playground
{
  "stylingRules": [
    {
      "symbolizer": {
        "fill": {
          "color": "lightSteelBlue"
        },
        "stroke": {
          "color": "steelBlue",
          "width": {
            "px": 3
          }
        }
      }
    }
  ]
}

Jérôme: intended, so that every feature type is visible by default, with the side effect on line vertices and polygon centroids; a single default Symbolizer is intended, so making the default depend on the geometry is not the fix, and a basic default style would normally clear the marker. The PR now says so in a NOTE. Open: how a style clears the marker. The draft renderer draws nothing for marker: { elements: [] }, but the JSON schema rejects an empty elements array (its oneOf branches overlap). Also open: the Dot defaults give a size and a color while a Dot is drawn with its Stroke's width and color. The other cards leave the default marker off, so they stay readable.

Which label priority wins#

What the draft says
/req/labels/label
  • An Encoding SHALL support defining a label Symbolizer property as a Label, which is a MultiGraphic that can contain multiple graphical elements.
  • A Renderer SHALL support drawing the graphical elements of the labels as a separate pass on top of all styled vector features and coverages.
  • A Renderer SHALL support omitting labels which cannot be placed without overlapping other labels.
/req/labels/placement
  • An Encoding SHALL support defining a placement Label property as a LabelPlacement object including a priority, a minSpacing and a maxSpacing.
  • A Renderer SHALL support placing labels so that a label with a higher priority is placed in preference to a conflicting label with a lower priority.
  • A Renderer SHALL support repeating a label so that the distance between repetitions of that label is at least minSpacing and, where space allows, at most maxSpacing.

Two nearby places whose labels overlap. Lillestrøm has priority: 2, Strømmen priority: 8. Only one label fits. Which one is kept?

Sources: gdaldem hillshade: azimuth 0 = from the top, 90 = from the east
