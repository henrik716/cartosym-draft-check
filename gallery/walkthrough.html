PR #133 walkthrough

CartoSym 2.0 Part 1 requirements and Part 2 gradient fills. Updated for the OGC CartoSym SWG meeting on 13 November 2026. Branch requirements-placeholders at 6da77bf; issues as of 11 November.

The PR replaces the placeholder text in Part 1 with normative requirements, puts every requirement on one identifier scheme, and moves gradients to Part 2. This page takes it class by class: what the PR chose, why, where the answer came from, and where the evidence is.

Where it stands

  • 31 of 50 choices follow answers from Jérôme and 4 do in part. The SWG agreed 3 on 6 November. 3 are the PR's own choices, and 9 are open. The rest are for the SWG to confirm.
  • 47 of 58 harness cases that libCartoSym could evaluate on 6 November agree with the draft. The other 11 are 9 reported bugs and 2 name differences.
  • No other renderer has run the render kits yet, so the rendered choices have no independent check.

Suggested for the meeting

  1. Decide #156: contains, startsWith and endsWith as functions with no prefix, as the PR now does, with Jérôme's agreement.
  2. Raise anything in the 34 answered choices that the SWG sees differently. New since 6 November: the NULL table (#155), dashPattern units (#161), six points from #162, and Consumers and Producers in the encoding classes.
  3. Go through the 7 proposals in section 6, as far as time allows.
  4. See who could help with the hatch angle, which needs input on graphics toolkits.

1. How the PR was made

Most requirements follow directly from existing text. These rules decided the rest.

  1. Existing text first. Requirements come from the clause text, the UML and CQL2.
  2. Two parts each. Each requirement says what an Encoding supports and what a Renderer does. In the CartoSym-CSS and CartoSym-JSON classes, a Producer and a Consumer take the place of the Encoding.
  3. libCartoSym breaks ties. Where the text is silent and libCartoSym has a default, the PR follows it, as with the hot spot and the tints.
  4. Minimal where unsettled. The requirement stays small and gets a TODO(review). Since Oct 19 each one points to an issue, as Jérôme asked.
  5. Render before deciding. Each judgement call has a gallery card showing the draft's choice next to the alternatives. Rendering surfaced the all-white example 6, the NDVI division and the default marker on every vertex.
  6. The PR follows the answers given in review. Where Jérôme answered a question on the PR or an issue, the PR followed, including reversals such as the hot spot and the casing width. These are proposals for the SWG to confirm.
Draft renderer
A small renderer written to do what the draft says, so each choice can be seen. It is a discussion tool, not a reference implementation.
Test harness
119 cases, with expected values taken from the requirement text, run through the implementations below.
libCartoSym
Ecere's library, and Jérôme's. cs-canif is its command-line tool, used here to evaluate expressions.
pycartosym
Maxime Collombin's library, used to read CartoSym-CSS and CQL2-Text and to check conversion.
Gallery and render kits
The gallery renders each judgement call next to its alternatives. A render kit holds the style, data and view of a card, so other renderers can draw the same map.

What Claude did

Drafted the requirement text, cross-checked it against the open issues, libCartoSym and pycartosym, and wrote the draft renderer and test harness.

What Henrik did

Set the direction, made the decisions on scope and conventions and on which questions to settle or leave open, and reviewed the results.

4. Where libCartoSym differs

The text was written from the spec, not from libCartoSym, and the comparison came afterwards. So each difference raised a question: should the text change, or libCartoSym? libCartoSym was followed where the text was silent. Where they differed, CQL2 and the spec's own examples came first, and the PR then followed Jérôme's answer.

47 of 58cases libCartoSym could evaluate on 6 November agree with the draft. The other 11 are 9 reported bugs and 2 name differences.

Why so many cases say unsupported

CartoSym Part 1 adds functions that CQL2 does not define, such as sin, round and upperCase. They have not been added to libCartoSym's evaluator yet, so cs-canif eval returns null, and the harness can only report that as unsupported. It means not implemented yet. It does not mean libCartoSym disagrees.

"I think I just never got around to align those extended functions introduced by CartoSym - Part 1 (not defined in the CQL2 standard)."Jérôme, libCartoSym#9, who plans to add them, starting with the ones the examples use

This cuts both ways: those 27 cases have no independent check yet, so for now only the draft renderer runs them.

Only 2 cases are about what the text should say, both about function names, with a proposal in #140.

5. Class by class

Classes appear in spec order. Answered means Jérôme gave that answer in a comment on the PR or an issue. It is not an SWG decision, and the final wording has not been reviewed. Agreed by the SWG means the group agreed the proposal in the meeting on 6 November, and the PR follows it. Partly answered items say which part is still the PR's own. Not yet reviewed means it is the PR's own choice and nobody has commented on it, so it is not agreed. The filter narrows the list.

Core

20 requirements and 1 recommendation in clause 7. Rendered and tested. The visualization time and capabilities identifiers are not implemented in the renderer.

The placeholders in clause 7 are filled from the clause text and the UML.

Does opacity apply to the whole symbol or to each part?

Answered by Jérôme

In the PR

It multiplies the opacity of the fill, the stroke, the marker graphics and the opacity channel of coverage cells. A NOTE says it does not apply to labels, and a recommendation applies it to fill, stroke and marker graphics together, so they do not show through each other.

Why

Jérôme's answer on #162. A label has its own opacity, as a MultiGraphic. Applied together, as SVG and CSS group opacity do, the overlap of fill and stroke does not show as a darker band. Jérôme pointed out that this needs an offscreen buffer and asked about the cost, so it is a recommendation. The draft renderer uses SVG group opacity, so it has no performance figures to offer.

#162 /req/core/opacity /rec/core/opacity-together Gallery card

Which zOrder is drawn on top?

Not yet reviewed

In the PR

A higher zOrder is drawn on top.

Why

Clause 7 said only that zOrder modifies the default order, with no direction, so the requirement states one. Listed on #162 with eight other points. Jérôme answered the others there and did not comment on this one, so it is still the PR's own choice.

#162 /req/core/z-order Gallery card

Does the default marker apply to every geometry type?

Answered by Jérôme

In the PR

Yes. A style that sets no marker draws a white 10 px Dot at each point, line vertex and polygon centroid. A NOTE says a base style normally unsets it for lines and polygons.

Why

Rendering raised this. Jérôme confirmed it is intended: points stay visible by default, and geometry-specific defaults would break the single default Symbolizer.

Gallery card 9485a89 83d613d

How does a CartoSym-JSON style clear the default marker?

Agreed by the SWG

In the PR

The NOTE says marker: null and marker: { elements: [] } unset it, and marker: { } keeps the default Dot, as Jérôme described. The JSON schema now accepts all three.

Why

Tested with Python jsonschema: anyOf in graphicArray fixes only { elements: [] }, and the other two need a change to marker. label takes the same change, and was tested the same way.

Agreed on 6 November

Make both schema changes, and test label the same way. Done in the PR.

Do gamma and gradients stay in Basic Vector Styling?

Agreed by the SWG

In the PR

No. Both are removed from this class, and gradient requirements move to Part 2.

Why

oertz said on #86 in 2024 that both leave Part 1 for Part 2. Only gradients have arrived there. Jérôme confirmed on #153 that gradients belong in Part 2, but has not commented on gamma.

#86 #153

Should Dot have size and color?

Answered by Jérôme

In the PR

Yes. They are the same values as its stroke's width and color: setting one sets the other, and the value set last applies. In Part 1 a Dot is always a filled circle. An outline is two concentric Dots.

Why

Table 22 gave a Dot size and color, but the class and schema did not have them. A design with fallback values was dropped because Jérôme wants them in sync, as in libCartoSym. A Dot is a stroke drawn on one point, as if a pen were put down and lifted.

Answered by Jérôme

In the PR

The center, { 0.5, 0.5 }.

Why

This is libCartoSym's default. Jérôme first said top-left, then took it back because centered icons are the common case. The PR followed both answers (83d613d, then 493953d).

/req/vector/image Gallery card 493953d

Do tint and blackTint belong in Part 1, and in which class?

Answered by Jérôme

In the PR

Yes, in /req/vector/image. Each component v becomes tint × v + blackTint × (1 − v). The defaults, white and black, leave the image unchanged.

Why

Jérôme confirmed the formula and the class. Recoloring a monochrome icon per category is common (MapLibre icon-color, QGIS SVG parameters), and the use case came from GeoServer in the Vector Tile Pilots.

Answered by Jérôme

In the PR

An Encoding stores it, and a NOTE says it is meant for picking. No Renderer requirement applies, but a permission lets a Renderer use it as an alpha-test threshold.

Casing and Centerline

2 requirements. Rendered.

Is the casing drawn beneath or above the stroke?

Not yet reviewed

In the PR

Beneath the main stroke.

Why

Drawn on top it hides the stroke, so it stops being an outline. libCartoSym models casing and center as StrokeStyling, as the draft does. Listed on #162 with eight other points. Jérôme answered the others there and did not comment on this one, so it is still the PR's own choice.

#162 /req/casing/casing Gallery card

What does the casing width measure?

Answered by Jérôme

In the PR

The distance it extends beyond each side of the main stroke, for a total of stroke width + 2 × casing width.

Why

Jérôme's answer, with a render. The first draft had it the other way round.

#147 Gallery card 62a3189

What happens where cased lines cross?

Answered by Jérôme

In the PR

Within a visualization pass, the casings of all features with the same zOrder go beneath the main strokes of those features. A NOTE allows single-pass methods such as signed distance fields if the result is the same.

Why

Casings of crossing lines merge, and a bridge with a higher zOrder keeps its casing over the roads below. This matches the painter's algorithm in clause 7, which is in a comment block.

Dashes, Hatches, Stipples, Dot Patterns

9 requirements and 1 permission in 4 classes. Rendered. Dot Pattern Fills is new in clause 2.

What unit is dashPattern in?

Answered by Jérôme

In the PR

Lengths are UnitValues, in pixels unless qualified. A Renderer supports pixels, points, millimeters, centimeters and inches. A permission in three parts covers meters and feet, percent of the stroke width for a stroke in display units, and percent of the stroke width for a stroke in meters or feet. The table, UML and schema had integers before.

Why

Jérôme's answers on #161: display units are required, percent gives MapLibre-like ratios, and real-world units are optional, since they may need a custom shader rather than a precomputed texture. He asked for the three cases to be separate parts of the permission.

Labels

2 requirements and 1 recommendation. Rendered; maxSpacing is not implemented in the renderer.

Are labels drawn with their feature or on top of everything?

Answered by Jérôme

In the PR

In a separate pass on top of all features and coverages. Omitting labels that cannot be placed without overlap is now a recommendation, unless a property of the Symbolizer allows the overlap.

Why

Drawn with the feature, a later feature can cover the label. Jérôme answered on #162 that omitting overlaps is the usual default but should not be required, since a future labeling extension, or a negative minSpacing, could allow overlaps. He did not comment on the separate pass.

Open

In the PR

Yes, a higher value wins.

Why

#148 Gallery card

Basic Coverage Styling

5 requirements and 1 recommendation. Rendered.

The spec's examples 5 to 9 are rendered on real data: Kartverket DTM for Rondane and a Sentinel-2 scene.

What range is colorChannels, and who scales the bands?

Partly answered

In the PR

Each component is 0 to 1. Example 6 scales the bands in the style, with colorChannels.r: B04 / 2500 and so on.

Why

Example 6 rendered all white without this. Jérôme's own style divides by 2500, but Jérôme said example 6 assumed pre-scaled bands and did not ask for it to change. The 0 to 1 range comes from the schema, and #150 may change the example again.

/req/coverage/color-channels Gallery card 1d69ffd

What about the default colorChannels, and which product is example 6 for?

Open

In the PR

The default still uses the first three fields unscaled. Example 6 assumes no offset, so B04 / 2500 comes out 0.4 too bright on Sentinel-2 L2A from baseline 04.00. Example 7 is affected too: the offset does not cancel in a ratio, so an NDVI of 0.71 comes out as 0.45.

Why

Scale and offset belong to the data product. Jérôme asked for a range of baselines rather than "or later", and suggested two kinds of style: one hardcoded per product, and one assuming a GeoDataClass that has already applied them.

Proposal

Examples 6 and 7 assume reflectance (B04 * 4). A second version handles digital numbers for baselines 04.00 to 05.11. The TODO becomes a NOTE: field values follow the logical schema, and a Renderer does not look up a product's scale. Posted on #150 on 6 November, waiting for Jérôme.

#150 Gallery card

How do colorMap and opacityMap treat values between and beyond entries?

Partly answered

In the PR

Exact at an entry, interpolated between entries, clamped outside the map. The method is left open, and a recommendation says the result SHOULD stay between the two closest entries.

Why

Clamping, exact entries and leaving the method open are Jérôme's answers. The recommendation is the PR's addition: Jérôme discussed overshoot on #149 and did not object, but has not confirmed it. libCartoSym's easing meets it, while a parabola through three entries can overshoot.

Expressions and functions

55 requirements and 1 recommendation in 10 classes: Arithmetic, Math, Conditional, Right-hand, Functions, Parameter Values, Variables, Text Relation, Text Manipulation, Array Relations. Tested in the harness.

Section 3 traces where these requirements came from, and section 4 covers libCartoSym. The entries here are the ones that involve a choice.

Is / real or integer division?

Answered by Jérôme

In the PR

/ is always real-valued, even for two integers. div is integer division.

Why

This follows CQL2, as Jérôme confirmed. Integer division turns every NDVI value in example 7 to 0, which the render showed, so an earlier plan to make / integer was dropped. Jérôme agrees libCartoSym should change.

/req/arithmetic/div Gallery card libCartoSym#11

How do intDiv and mod round?

Answered by Jérôme

In the PR

intDiv truncates toward zero, and mod takes the sign of the first operand.

Why

Jérôme answered on #162 that these follow C-style languages (eC, C++, Java, JavaScript), while mathematics and Python differ, and that it is worth raising with OGC API - Features for CQL2. libCartoSym agrees on -7 % 3 but crashes on div.

#162 /req/arithmetic/int-div /req/arithmetic/mod

How does round treat halves, and is rint needed?

Answered by Jérôme

In the PR

round takes halfway cases away from zero, as C does, so round(-2.5) is -3. rint is removed. The other math functions have their usual meaning, with angles in radians.

Why

The earlier text followed Java's Math: round toward positive infinity and rint to the even value. On #162 Jérôme asked whether rint was needed beside round, agreed to remove it, and said he intended the C rules throughout. libCartoSym does not evaluate these yet (libCartoSym#9), so only the draft renderer checks them.

What happens when an operand is NULL?

Answered by Jérôme

In the PR

Operations with a null operand follow CQL2, and a selector evaluating to null does not select the feature. /req/conditional/else-exp takes the else branch when the condition does not evaluate to true. A Symbolizer property whose expression evaluates to NULL takes a value by its data type: 0 for a number, false, black for a color, the empty string, the default for an enumeration, and null for a Marker or Label, which empties its graphical elements. A recommendation says to report it, unless the property is set to null directly.

Why

Jérôme's answers on #155. He found "draws nothing" too strong: it hides problems, and one bad property would hide the rest of the Symbolizer. Casting opacity and visibility to 0 and false as well keeps the rule simple, and the effect still shows. For an enumeration he agreed to use the default.

How do CartoSym-CSS selectors combine?

Answered by Jérôme

In the PR

Expression selectors combine with AND. Only short-hand data layer names combine with OR, and the two groups with AND. A NOTE says that [dataLayer.id = 'Roads'][dataLayer.id = 'Railways'] never matches, and clause 17 has Jérôme's example, Roads Railways[viz.sd < 10000][level < 4].

Jérôme's answer on #162: the OR applies only between short-hand names, and "data layer names" alone could be misread. pycartosym 0.6.3 and earlier joined several names with AND. 0.6.4 joins them with OR (pycartosym#169), and the draft renderer now uses 0.6.4.
