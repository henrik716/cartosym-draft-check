# Notes: places where the text leaves the result open

Code is in `evaluator/` (`cs.py`, `run.py`). All 123 cases have a result in `results.json`. Where a case has `cql2_json` I evaluated that; otherwise I parsed `cql2_text` with a hand-written parser that follows the precedence order of the ANTLR grammar.

## Null handling

1. /req/core/operations, "A Renderer SHALL support evaluating operation expressions with a null operand as specified by CQL2." CQL2 is not in the folder, so the rule is not given. Readings: (a) any null operand gives null for every operator; (b) SQL-style three-valued logic, where `and`/`or` can still give false/true. Implemented (b). Results: `null + 1`, `null = 1`, `null <> 1`, `null > 1`, `null like 'a%'` and `not (null > 1)` give null. `null and false` gives false, `null or true` gives true, `null and true` and `null or false` give null. `(null+1) is null` gives true. The text does not say which reading applies to `and`/`or`.
2. /req/core/relational, "`is` ... Only used with `null` literal for second operand". `x is null` is implemented as `isNull(x)`, which is never null itself. `x is 5` is not defined; I raise a parse error in text.
3. /req/core/selector NOTE says a null selector does not select. Fine, but /req/conditional/else-exp says "when its `condition` does not evaluate to true". I implemented null condition goes to `elseExp`. /req/conditional/condition says the condition is "an Expression evaluating to a boolean value", so a non-boolean or null condition is formally not allowed. Other reading: the whole conditional is null. Not tested by a case.
4. /req/functions/call-expressions says a function call with a mismatched argument count or type "SHALL evaluate ... to NULL". This conflicts with the README's `{"error": ...}` option. Implemented NULL, not an error (`fn-wrong-arity`, `fn-wrong-type`, `fn-standard`). A null argument is also a type mismatch and gives null.
5. /req/core/not (the Logical Operators table): "not: True if and only if the operand is false". Read literally, `not null` is not true, which does not decide between null and false. Implemented null (three-valued logic).

## Arithmetic

6. /req/arithmetic/*: the number type of results is not said. Implemented: integer op integer gives integer for + - * div % (and ^ with a non-negative integer exponent), `/` always gives a real. Result `7/2` = 3.5, `7 div 2` = 3, `2^10` = 1024 (integer; 1024.0 is the other reading). In JSON the two are numerically equal.
7. /req/arithmetic/div, "the real-valued quotient ... including when both operands are integers", while the lexer/grammar uses `/` and the table names the operator `div`, and the CSCSS word `div` is IDIV (integer division). The same word `div` therefore names two operations: the requirement `div` (real quotient, symbol `/`) and the keyword `div` in the grammar (integer quotient, requirement `intDiv`). Implemented: `/` is real quotient, text `div` is intDiv (truncation toward zero). In CQL2-JSON, I accept both `div` and `intDiv` as integer division, and `/` as real. If JSON `"op":"div"` was meant to be the real quotient, `div` there would be ambiguous. Not tested by a JSON case.
8. /req/arithmetic/mod: "the result has the sign of the first operand" (`-7 % 3` = -1). Clear. Real operands (e.g. `7.5 % 2`) are not said; I used C `fmod`.
9. Division and modulo by zero, and integer overflow are not defined. Implemented null.
10. Precedence of unary minus. The grammar lists the unary arithmetic operator as the first (tightest) alternative, so `-2 ^ 2` parses as `(-2)^2` = 4, unlike usual mathematics. Implemented as the grammar says. `-7 div 2` and `-7 % 3` give the same result either way.
11. Associativity of `^` is not stated (ANTLR default: left). Implemented left. `a < b < c` is accepted by the grammar and is parsed left-associatively; it compares a boolean with a number and gives null.
12. Operators applied to non-numeric operands (`'a' + 1`) are not defined. Implemented null.
13. Precedence between `not` and relational operators: the grammar puts relational and `between` above `not`, and `not` above `and`. `not a = b` is `not (a = b)`. The text of clause 7 never states precedence; I took it from the grammar only. Also the `between` bounds are arithmetic only (grammar `betweenBound`).

## Math functions

14. /req/math/*: the UML gives `ceil(x: double) double` and `round(x: double) long`, but /req/math/ceil says "smallest integral value". Implemented `ceil`/`floor` as a real (`-2.0`) and `round` as an integer (`3`). Integer 3 vs 3.0 is not decided for ceil/floor.
15. /req/math/round: "rounding halfway cases away from zero": `round(2.5)` = 3, `round(-2.5)` = -3 (not banker's rounding). Clear.
16. /req/math/max, /req/math/min: "taking two numeric arguments" and the UML has two parameters. `max(1, 5, 3)` therefore has the wrong number of arguments, and by /req/functions/call-expressions gives NULL. The other reading (variadic max, as in many CQL2 profiles) would give 5. Implemented NULL. The case `fn-standard` is named "standard functions", so a variadic reading may have been intended; the text says two.
17. Domain errors (`sqrt(-1)`, `log(0)`, `acos(2)`) and NaN/infinity results are not defined. Implemented null.
18. /req/math/random: "pseudo-random ... >= 0 and < 1". The only checkable property; no seed or distribution given.
19. /req/functions/call-expressions: "converting an integer argument to a real number" is implemented implicitly (Python ints are accepted for double parameters). A boolean is not a number (it does not convert).
20. /per/functions/type-casts: "A Renderer MAY convert arguments of other types ... How such arguments are converted is not specified." Implemented no conversion (text is not converted to a number), so `pow('a', 2)` is null. A renderer using the permission could differ.
21. Function names are matched case-sensitively as written in the tables (`startsWith`, `a_containedBy`); the text does not say whether names are case-insensitive as CQL2-Text keywords are.

## Text functions

22. /req/text-relation/like: "`%` ... matches any sequence of zero or more characters and `_` matches exactly one character". Escaping is not mentioned. In `'50%' like '50\%'` the pattern is `50\%`. Readings: (a) backslash escapes `%`, so the pattern means literal `50%` and the result is true (CQL2 does this); (b) backslash is an ordinary character, so the pattern needs a literal `\` after `50` and the result is false. Implemented (b), because the text only defines `%` and `_`. Also: case sensitivity of `like` is not stated (implemented case-sensitive), and `_` matching one "character" (code point vs UTF-16 unit vs grapheme) is not stated (implemented code point).
23. /req/text-relation/not-like: "logical negation of the equivalent `like`". With a null operand the negation is null (consistent with item 5). The JSON schema has no `notLike` (a TODO in the text). In CQL2-Text the production is `not like` and I translate it to `notLike`.
24. /req/text-manipulation/case-insensitize: names are `caseInsensitize` / `accentInsensitize` in the requirements, but `casei` / `accenti` in the JSON-based cases (the text has a TODO to align them). The requirement says "(equivalent to the CQL2 CASEI function)" so I accept both names as aliases. Reading B (the unlisted name `casei` is an unknown function, giving an error or NULL) would change `textfn-casei`, `textfn-accenti`, `textfn-accenti-o-stroke`.
25. /req/text-manipulation/case-insensitize: "two strings differing only in letter case compare as equal". The folding is not defined (casefold vs lower vs upper, e.g. `ß`). Implemented Unicode `casefold`.
26. /req/text-manipulation/accent-insensitize: the NOTE says CQL2 names no table. Implemented: Unicode NFD, drop the combining marks, then fold `Ø ø Ł ł Đ đ` to the base letter (the NOTE says Ø and Ł fold); `ß` and `Æ` stay unchanged. The NOTE leaves other non-decomposing letters (e.g. `đ`, `ħ`, `ı`) unspecified; my choice of Đ/đ is a guess. The Japanese dakuten are not handled specially (NFD would remove them; the NOTE says they are not removed), which I did not implement for lack of a case.
27. /req/text-manipulation/lower-case, upper-case: locale and special casing (`ß` to `SS`, Turkish `i`) are not stated. Implemented Python's default Unicode full case mapping.
28. /req/text-manipulation/substitute: "`s` with occurrences of `a` replaced by `b`". All occurrences vs first, overlapping occurrences, and empty `a` are not stated. Implemented all non-overlapping occurrences, left to right; an empty `a` returns `s` unchanged.
29. /req/text-manipulation/format: "conversion specifiers of the C `printf` function (ANSI C)". Behaviour with a missing or extra argument, a type that does not match the specifier (for example `%d` with a real, `%s` with a number), and `%n`/`%p` is not specified. Implemented: `%d` with a real truncates to integer, a count mismatch or a non-numeric argument for a numeric specifier gives null; `%s` of a non-text uses its JSON form. The NOTE says the arguments "match when they match the conversion specifiers", so a mismatch gives null by reading of /req/functions/call-expressions, but how strict the match is (`%d` for 3.0) is open.
30. /req/text-manipulation/concatenate: takes exactly two arguments per the table (`concatenate(string a, string b)`); `concatenate('a','b','c')` would be NULL. No case.
31. /req/text-relation/contains etc.: "substring" with an empty second argument is not stated (implemented true). Comparison is by code point, case-sensitive.
32. Strings in the grammar: the lexer accepts both `''` and `\'` as an escaped quote inside a character literal, and the `CHARACTER_LITERAL` rule joins adjacent literals separated by whitespace (`'a' 'b'` is one literal). Implemented joining, but the concatenation of adjacent literals has no stated value (does it add a quote between, as in SQL? implemented: just joined).

## Relations, arrays, comparisons

33. /req/array-relations/a-equals: ordered comparison ("each element of `a` is equal to the element of `b` at the same position") is explicit in the requirement. A TODO comment in the same file says CQL2 evaluates arrays as sets and that this is "not settled (see #154)". Implemented the requirement text: ordered, so `a_equals((1,2),(2,1))` is false. Under the CQL2 set reading it would be true.
34. /req/array-relations/*: "element of" and "equal" for mixed types (1 vs 1.0, nested arrays, null elements) are not stated. Implemented Python equality, except that a boolean never equals a number. Empty array cases (`a_contains(a, ())` true, `a_overlaps` with an empty array false) follow from the wording ("every element of ...") but are not stated explicitly. The "elements" are ordered with duplicates allowed; whether duplicates matter is not stated (ignored).
35. Parentheses: in the grammar `(1, 2, 3)` is an array (`expArray`), but `(1 + 2)` is a parenthesized expression, and `(1)` is ambiguous between a one-element array and a parenthesized `1` (and a tuple `a b` is a third form). Implemented: a parenthesized list with no comma is a grouping, not an array. Therefore `2 in (2)` would have a non-array right side and give null.
36. /req/core/relational: `in` "Only used with an array for second operand". With a non-array right operand the result is not defined; implemented null. Equality semantics for `=` between different types (text vs number, text vs boolean) is also not defined; implemented null. Comparison of booleans with `<` is not defined; implemented null. Equality of text is code point, case-sensitive.
37. /req/core/relational: `between` "inclusively". Implemented `lo <= x <= hi`; with `lo > hi` it is false (not symmetric). `not between` is the negation, so a null gives null.
38. `=` on arrays and on null: `null = null` is not defined by the text. Implemented null (item 1b); `is null` is the way to test it.
39. Keywords: the lexer makes `and`, `or`, `not`, `in`, `is`, `like`, `between`, `div` case-insensitive (the cases use `AND`). `true`, `false`, `null` are not tokens in the lexer, they are IDENTIFIERs in the grammar, so formally `null` is an identifier. Clause 7 and /req/core/literals say `true`/`false`/`null` are literals; implemented as literals (case-insensitive), and a double-quoted `"null"` as an identifier. `[a = null]` is syntactically valid but not defined (gives null).
40. Lexer: the unit abbreviations (`m`, `px`, `pt`, `pc`, `em`, `ft`, `cm`, `mm`, `inch`) are lexed as UNIT tokens before IDENTIFIER, so a property or function named `m`, `pc`, `cm` ... cannot be used as an identifier in CartoSym-CSS even though CQL2 allows it. Implemented as in the lexer (such a word is a UNIT token, so using it as a property gives a parse error); not tested. Expressions with units (`5 m`) are accepted by the grammar but have no defined value in arithmetic/comparison; implemented as a parse error in the evaluator (no case).

## Variables, identifiers, system identifiers

41. /req/variables/definition: "allowing an application to override the value of a defined variable". Readings: the override replaces the value, or the override is an expression evaluated in the definitions' context. Implemented replace (`var-override` = 10). Overriding variables with the name of an undefined variable, and a variable referring to itself, are not defined (undefined variable gives null; cycle is an error).
42. /req/variables/expression: "the current value of the referenced variable". For a variable defined by an expression (`double = base * 2`), the text does not say whether it is evaluated per use (so a changed `base` override changes `double`) or once at definition time. Implemented evaluated at use with the current overrides.
43. /req/core/expressions-field-identifiers: a feature property that does not exist. The text does not say (null? error?). Implemented null. Identifier lookup is case-sensitive, and a double-quoted identifier is the same as the unquoted name; not stated.
44. /req/core/expressions-system-identifiers: the clause uses `visualization.scaleDenominator`, the examples and case use `viz.sd` (a short form that is not defined in the requirements). Implemented `viz.sd` as an alias of `visualization.scaleDenominator` and `viz` of `visualization`; a case that gives `system` under `viz.sd` also works since I look up the name as given first. The set of aliases is not defined in the text. /req/core/time lists `visualization.timeInterval` which is not in the first list of the System Identifier enumeration, and the `capabilities.*` ones are not given values in the cases.
45. In text, member access on an identifier (`a.b`) is treated as one dotted name, either a system identifier or a property name with a dot; the grammar has "Member access" as a generic production but does not say which meaning applies. In text without JSON I resolve properties by the dotted name.

## Conditionals and parameters

46. /req/conditional/*: `?:` right-associative (grammar says so), lowest precedence. The text names no operator in the table. A non-boolean condition: see item 3. Both branches are evaluated lazily (only the selected one); only matters for errors.
47. /req/parameter-values/null: the null table is for Symbolizer properties and not for expressions evaluated as selectors, so selector null handling comes from /req/core/selector NOTE. Not exercised by the cases (no symbolizer property context was given).

## Style cases (/req/core/relational, /req/cscss/grammar)

48. The three style cases use `opacity: 0.5;` inside the rule braces, which the grammar accepts (`propertyAssignment: lhValue COLON expression`), while clause 7 examples use `opacity = 1.0;` and `stroke: { gray }`. The grammar and the examples disagree on `=` vs `:` for assignment (the grammar's `EQ` is only used in `variableDef`). I judged by the grammar. All three are valid: `<>` is the NEQ token and wins by longest match over `<` and `>` (so `[a<>1]` without spaces is fine), and the relational operator binds tighter than `and`.
49. The grammar's `stylingRule` requires `;` only between assignments, and `(propertyAssignmentList SEMI)?` means a trailing `;` is required after the last assignment. `{ opacity: 0.5 }` without the final `;` is invalid under the grammar, yet the examples in clause 7 (`[viz.sd < 10000] { stroke: { blue, width: 5m } }`) leave it out. Not exercised by the cases; my checker follows the grammar (the final `;` required).

## Other

50. Several cases contain non-ASCII text (`café`, `Øre`); I read `cases.json` as UTF-8 and the results are for the real characters. Under a wrong code page the inputs look like `cafÃ©`, and the folding would then not match.
51. The number literal grammar accepts `7.` and `.5` and exponents; `+` as a unary prefix is accepted by the grammar and ignored. Integers beyond int64 are not defined (Python big ints used). Integer literal vs real literal: `3.0` is a real, `3` an integer; `3.0 = 3` is true (numeric comparison across types), which the text does not state.
52. Literal output: where the case result is a real (`2.5`) I report a JSON number; for an exact integral real such as `ceil(2.5)` I report `3.0`.
