# Notes: choices left open by the requirement text

Renderer: `renderer/render.py` + `renderer/expr.py`, run with
`uv run --no-project --with numpy --with pillow --with skia-python python renderer/render.py`.
skia-python is used only as a general 2D graphics library (anti-aliased paths, strokes, dashes, clipping, TrueType text). All 20 cases render (21 images, `vector-units` has two views).

Each entry: requirement (or clause/table) — words that leave it open — readings considered — **implemented**. The tag (N-xx) is the one used in the code comments.

## A. Rules, selectors, symbolizer resolution

1. **N-UNSELECTED** — /req/core/symbolizer: "portraying data using the Symbolizer properties resulting from all selected StylingRules, using the default values for properties not set by any selected rule"; NOTE under /req/core/default-values: "so that every feature is visible by default". Open: is a feature that no rule selects portrayed at all? Readings: (a) yes, with all defaults (visibility true, white fill, 1 px black stroke, default white 10 px Dot); (b) only features selected by at least one rule are drawn (SLD habit). **(a)**. Visible in `core-opacity`: non-lake polygons are drawn with a white fill, a black 1 px outline and a white Dot at their centroids.
2. **N-OVERRIDE** — /req/core/rules: a later selected rule's properties "SHALL be interpreted as overriding all Symbolizer properties set by earlier rules". Readings: (a) a later rule replaces the whole symbolizer; (b) each property it sets replaces that property (the cascading reading of the overview and of clause 17). **(b)**: per property; an object value without `alter` replaces the whole object, so its unset members go back to their defaults (e.g. `core-time` replaces the stroke as a whole).
3. **N-ALTER** — /req/json/partial-update, /req/core/instances. Open: what an `alter: true` object merges onto when no earlier rule set that property. **Merged onto the default object** (default Fill/Stroke/Marker); for `color` with `alter`, the earlier colour (name/array) is converted to r,g,b first. Array-element updates (`{index, value}`) pad with nulls if the index is past the end (undefined).
4. Dot `size`/`color` vs `stroke.width`/`stroke.color` (/req/vector/dot, /req/json/dot-size-color): "the value set last applies". Implemented across rules during the merge; not exercised by the cases.
5. **N-NULL** — /req/core/operations: "evaluating operation expressions with a null operand as specified by CQL2". The CQL2 text isn't included here. **Three-valued logic**: comparison with null → null; `and` = false if any operand is false, else null if any is null; `or` mirrored; a null selector does not select (NOTE under /req/core/selector). So `elevation >= 2000` doesn't select places without `elevation` (`font-outlines`), and `marked = true` doesn't select roads without `marked`.
6. **N-SYSID** — names differ between the text and the JSON schema: clause 7 has `dataLayer.identifier`, `visualization.scaleDenominator`; the schema enum and all cases use `dataLayer.id`, `viz.sd`, `viz.timeInterval.start.date`; clause 8's table has `feature.geometryDimension` and `dataLayer.featuresGeometryDimension`, while its UML, the defaults NOTE and the schema use `...Dimensions`. **Treated as aliases.**
7. **N-ENUM** — `dataLayer.type = "vector"` in JSON: JSON can't tell an enumeration literal from a text literal. Clause 17 says that in CSS `vector` and `'vector'` are equivalent; nothing equivalent is said for JSON. **Compared as text.**
8. **N-DATECOMPARE** — /req/core/time; README: `validDate` is an ISO date held as a GeoJSON string. Comparing a text property with `viz.timeInterval.start.date` (a Date) isn't defined. Readings: (a) error/null (type mismatch); (b) coerce ISO text to a Date; (c) compare as strings. **(b)**. (b) and (c) give the same result here. The view gives a `date` and a `timeInterval` of dates but no time: `viz.dateTime` = that date at 00:00, and interval ends = dates at 00:00. Contradictions in clause 7 (not used): `visualization.timeInterval` is defined as "Current visualization time of day"; TimeOfDay table gives `minutes` type Month and `seconds` int (UML: double).
9. Coverage selectors (/req/core/selector: "to a feature or coverage cell"): **selectors are evaluated with per-cell arrays**, but only a selector that has the same result for every cell is supported. All coverage cases select by `dataLayer.id`.

## B. Draw order, opacity, zOrder

10. **N-ZORDER** — /req/core/z-order: "portraying features and coverage cells of a single rendering pass in increasing order of their resolved zOrder". Open: is zOrder compared across layers or only within a layer? What breaks ties? Is it int (Symbolizer table, schema numericExpression) or float (the "Visual Ordering Constructs" table)? **Global across layers. Ties keep the view's layer order, then the feature order in the file. Compared as numbers.** Default 1.
11. **N-DRAWORDER** — not stated: the order of fill, stroke and marker within a feature. **Fill, then stroke, then marker elements in array order (first at the bottom).** The order of elements follows the NOTE under /req/vector/dot ("the larger one first"). Annex F (informative) says fill before stroke.
12. **N-OPACITYGROUP** — /req/core/opacity "multiplying it with the opacity of the fill, the stroke, the graphics of markers" vs /rec/core/opacity-together. **Grouped per feature**: fill+stroke+marker composited in an offscreen layer, then drawn at `opacity`. So two overlapping features still show through each other. Casing and centre lines are drawn in their own sub-passes (see 23–24), so for them the opacity is multiplied in directly (not grouped). Labels: not affected (NOTE).
13. Visibility false also hides the feature's label (/req/core/visibility: "not portraying a feature").

## C. Units

14. **N-UNITS** — /req/vector/units lists "pixel, millimeter, inch, percentage, meter, foot"; clause 8 lists pixel, millimeter, inch, percentage, meter, foot; the GraphicalUnit enum adds points, em, screenCM; /req/dashes/dash-pattern requires "pixels, points, millimeters, centimeters and inches"; clause 17 defines px, m, ft, pc, pt, em, inch, cm, mm; the schema uses `in` (not `inch`). The lists are inconsistent. **All of px, mm, cm, in, pt, em, pc, m, ft are accepted.** Unitless → px ("For screen-space objects, defaults to pixels"). 1 px = `pixelSize_mm` (0.28 mm).
15. Ground units: "m" → pixels by dividing by the view's metres per pixel (bbox width / width). This equals `scaleDenominator` × 0.28 mm in every view. Open: CRS (projected UTM) metres vs true ground metres (the UTM scale factor here is ≈1.0005). **CRS metres.**
16. **pc** — clause 17 defines `pc` as "percent", but in CSS `pc` means pica (1/6 in). The JSON `vector-image` case uses `{"pc": 50}` for the hotSpot. **Percent.** Percent of what is said only for hotSpot/scaling ("meaning depends on context").
17. `em` — clause 17: "One em is equal to the target's selected or default font point size". This is a number of points, not a length in px. It is not used in the cases; implemented as the font size in px.

## D. Strokes, dashes, casing

18. **N-STROKEPOS** — not stated whether the stroke is centred on the geometry or drawn inside the polygon. **Centred.** Polygon strokes outline all rings, including holes (clause 8 gives "the exterior of a polygon geometry" only as an example).
19. **N-MITER** — clause 8: "at the corners of paths are miter joined". There is no miter limit. **4** (the SVG/skia default). Caps butt as stated.
20. **N-ZEROWIDTH** — `vector-marker-dot` lakes: `stroke: { width: 0 }`. Readings: no stroke / hairline. **No stroke.** The colour then defaults to black, which doesn't matter.
21. **N-DASHOFFSET** — /req/dashes/dash-offset only says "dashing vector geometry based on a dashOffset property"; the figure caption (figure not included): "a dash pattern preceded by an offset". Readings: (a) SVG `stroke-dashoffset`: start `dashOffset` *into* the pattern (the line starts with a 4 px dash for `[8,4]`, offset 4); (b) the pattern is shifted forward along the line, so the line starts with `dashOffset` of gap, then the pattern. **(b)**, following the caption. Also open: whether the pattern restarts per feature, per part, or runs continuously across features. **It restarts at the start of each line part.** An odd number of lengths is repeated twice (SVG habit; undefined). The units of `dashOffset` aren't stated (only dashPattern's are); **same units as dashPattern.**
22. **N-CASINGDEF** — /req/casing/casing. Defaults for casing/centre `color`, `opacity`, `width` aren't given. **Black, 1, 1 px.** Total width = main width + 2 × casing width (as stated). The casing's caps/joins follow the stroke (butt/miter). Butt caps leave notches where two road features meet end to end at an angle; the requirement that casings "merge" doesn't address caps.
23. Casing sub-pass scope: "the casings of all features with the same zOrder beneath the main strokes of all those features". Open: across layers? **Yes**, all layers in that zOrder.
24. **N-CENTER** — /req/casing/center: "on top of the main stroke". Readings: (a) each feature's centre line right after its main stroke; (b) all centre lines after all main strokes of the zOrder (mirroring the casing). **(b)**: with (a), later features' main strokes cut the centre lines at junctions.
25. **N-CENTERNAME** — the text says `center`; the schema has `centerLine` (TODO #120); the case uses `center`. **Both accepted.**

## E. Fills and patterns

26. **N-HOLES** — fill rule not stated. **Even-odd** over all rings of a polygon (holes are not filled).
27. **N-PATTERNFILL** — /req/hatches/hatch, /req/dot-patterns/dotpattern, /req/stipples/ratio. None of them says what colour the lines/dots are drawn in, or whether `fill.color` is still painted as a solid background. Readings: (a) pattern drawn in `fill.color`/`fill.opacity`, no solid fill; (b) solid fill in `fill.color` plus a pattern in another colour (stroke colour? black?); (c) both in `fill.color` (the pattern would be invisible). **(a)**.
28. **N-HATCHDEF** — Hatch defaults are given only by a figure caption: "Default hatch properties (width : 1 px, angle : 45 °, distance : 10 px)". **Used as defaults.** `distance` is "Distance between two consecutive hatches". Readings: centre-to-centre vs gap between lines. **Centre-to-centre, measured perpendicular to the lines.**
29. **N-HATCHANGLE** — Hatch table: "Hatches orientation clockwise degree"; the TODO (#146) says other angles start "at 0 pointing right and turn counter-clockwise". The reference direction of 0 isn't given. **0 = horizontal lines; positive angles turn clockwise on screen** (45 → lines from top-left to bottom-right; 90 → vertical).
30. **N-PATTERNORIGIN** — pattern phase/origin not stated (polygon bbox, centroid, map origin). **Anchored to the map's pixel origin (0,0)**, so neighbouring polygons line up.
31. **N-DOTSIZE** — dot pattern dot size and colour undefined (TODO #84); /req/dot-patterns/distance only gives spacing. **Filled circles 2 px in diameter in `fill.color`, at ((i+½)·horizontal, (j+½)·vertical) px**, in a rectangular (not staggered) grid.
32. **N-STIPPLE** — Stipple `ratio`: "Ratio of stippling dots according to area filled" (TODO #84 for size and colour). The distribution (random, blue noise, regular), the dot size, and whether the ratio is the covered fraction of the area or a density are all undefined. **1-pixel dots at pseudo-random pixels; each pixel is on with probability `ratio` (≈30 % of the area covered), from a fixed seed so the result is reproducible.** Another renderer will not produce the same pixels.

## F. Markers and graphics

33. **N-CENTROID** — /req/vector/marker: "at the centroid of polygons". Centroid type not stated: area centroid (can fall outside a concave polygon, e.g. a curved lake), point-on-surface, or label point. One marker per MultiPolygon or per part? **Area-weighted centroid with holes subtracted, one per feature.**
34. Line markers: /req/vector/marker "at the points of vector geometry (for points and line strings)"; overview "at each point of line geometry". Readings: every vertex vs end points only. **Every vertex**, including first and last (`vector-marker-dot` paths are dotted at every vertex).
35. **N-YAXIS** — /req/vector/graphics: "a uom-qualified 2D real position offsetting the graphic". The direction of +y isn't stated (screen down or map up). **+y is up** (map convention). Evidence: `vector-text` puts the elevation at `0 -6` with `alignment: center top`, which only makes sense below the dot if y is up and "top" is the text's top edge. With y down, "top" would have to mean "placed above the anchor", and then `left` at `6 0` would put the name over the dot. Effect: in `vector-marker-dot` the small Dot at `12 -12` is lower-right of the hut. In `labels-priority` the names sit 8 px above the dots.
36. **N-NEGSIZE** — `core-parameters`: size = (elevation − 900)/100 gives −0.22 for the 878 m spot height. A negative size isn't defined. **Nothing drawn** (also for size 0).
37. Dot with `stroke.opacity`: **multiplied with the Graphic opacity.** The marker's own (MultiGraphic) `opacity`/`position` apply to all of its elements.
38. **N-RESOURCE** — the Resource class has `url`; the schema and the case use `uri`. Which wins when both `uri` and `path` are given isn't said, and the base of a relative `path` isn't said. **The local `path` wins, resolved against the style file's folder.** (README: `../icons/` from the case folder.)
39. **N-IMAGESIZE** — Part 1 has no size/scale for an Image. **Drawn at its native size, 1 image pixel = 1 output pixel (24×24 px).** At another display resolution, other readings would scale it.
40. **N-IMAGESNAP** — sub-pixel placement isn't stated. **The top-left corner is rounded to whole pixels** so the icon stays sharp.
41. **N-HOTSPOT** — Image table: "hotSpot | 0,0 position in the image | UnitPoint (uom-qualified)"; default `{ 0.5, 0.5 }` = centre. That makes unitless values fractions, while clause 17 says unitless values of screen-space objects are pixels. Also undefined: which corner is the origin, and the direction of y (the `50 pc 100 pc` = "bottom centre" comment implies y down from the top, the opposite of N-YAXIS). **pc = percent of the image size; unitless = fraction of the image size; px etc. = pixels from the top-left; y down within the image.**
42. Tint: /req/vector/image `tint × v + blackTint × (1 − v)`. Open: the colour space (sRGB values vs linear), and whether premultiplied values are used. **sRGB, unpremultiplied.** `alphaThreshold`: the permission (alpha test) isn't used.

## G. Text, fonts, labels

43. **N-FONTFACE / N-FONTDEF** — the Font table in clause 8 has only face/size/bold/italic. The UML and the schema add `color`, `opacity`, `underline`, and `outline` comes from the font-outlines class. There are no defaults for face, size, colour or opacity, and no rule for fallback when a face is missing. **Arial; 10 pt; black; opacity 1. "Arial" → arial/arialbd/ariali/arialbi.ttf; unknown faces → Arial.** Size: "Size of the font (pt)" is taken as the em size: 1 pt = 25.4/72 mm = 1.26 px at 0.28 mm/px.
44. **N-TEXTCONV** — `text: elevation` resolves to an integer. The conversion of numbers to text isn't defined (decimals, thousands separators). **Plain decimal; integral reals without ".0"; null → empty string (nothing drawn).**
45. **N-ALIGN** — /req/vector/text gives the alignment enum but not its meaning. Readings for `left`: the text starts at the anchor vs the text lies left of the anchor. For `top`/`middle`/`bottom`: top/middle/bottom of the ink box vs of the font's ascent–descent box vs baseline. **left/center/right = the text's left edge/centre/right edge at the anchor; top/bottom = the font's ascent/descent line at the anchor; middle = halfway between them.**
46. **N-ALIGNDEF** — default alignment undefined. **center, middle.** The key names disagree: clause 8 table `horzAlignment`/`vertAlignment`; UML and CSS `horizontal`/`vertical`; schema `hAlignment`/`vAlignment`. **All accepted**, plus the 2-element array form used by the cases.
47. **N-OUTLINE** — FontOutline `size` is a plain "float" (not uom-qualified), so its unit (px? pt like the font size?) is open. Defaults for size/colour/opacity are undefined (`labels-spacing` omits `opacity`). **px; outline drawn as a stroke of width 2×size around the glyph contours with round joins, beneath the glyph fill; defaults size 1 px, white, opacity 1.**
48. **N-LABELS** — anchor of a label: for points the point (plus element `position`); for polygons **the centroid**; for lines nothing is said. Overlap test (/rec/labels/overlap) **uses the text boxes (including the outline) and only other labels, not markers or lines.**
49. Priority (/req/labels/placement, TODO #148 "confirm that a higher priority value means a higher priority"). **Higher value first; ties by layer/feature order.** No default priority is given: **0**. A null priority (peaks without `elevation`) → 0 per the null table of /req/parameter-values/null (numbers → 0), so they are placed last.
50. **N-LINELABEL / spacing** — /req/labels/placement: "repeating a label so that the distance between repetitions of that label is at least minSpacing and, where space allows, at most maxSpacing". Open:
    - (a) Is "that label" one feature's label, or all labels with the same text? Roads are split into many features. **Same text across the layer.**
    - (b) Is the distance measured along the line or straight? **Straight distance in pixels between anchors.**
    - (c) Where does the first label go? Where do candidates come from? **Candidates every 4 px along each line from its start, accepted greedily.**
    - (d) With no `maxSpacing`, nothing forces repetition beyond what the greedy pass gives.
    - (e) Orientation along the line vs horizontal: **horizontal, centred on the line.**
    - (f) With no `minSpacing` on a line: **one label at the middle.**
51. **N-LABELINSIDE** — not stated whether labels may be cut by the map edge. **A label is only placed if its box lies fully inside the image.**
52. Labels pass: "a separate pass on top of all styled vector features and coverages". **Drawn after all zOrders; unaffected by Symbolizer opacity** (NOTE under /req/core/opacity). Text graphics in a *marker* (`vector-text`) are drawn in the feature pass with no collision handling, so overlapping marker texts are kept.

## H. Coverages and hill shading

53. **N-RESAMPLE** — how cells are resampled to the output pixels isn't stated (nearest vs bilinear vs cubic). /req/hill-shading/hill-shading says the normal is computed from "neighbouring samples of the elevation coverage at the resolution being rendered". **Bilinear interpolation between cell centres to each output pixel centre (clamped at the edges); pixels whose centre is outside the grid are transparent.** With 150 m cells drawn at 28 m/px (`font-outlines`), bilinear upsampling plus per-pixel differences makes the gradient constant within each cell quad, so the relief looks faceted. Nearest neighbour would give flat steps; cubic would look smooth. The three choices give clearly different images.
54. **N-HSGRAD** — "differences in elevation between neighbouring samples … over the horizontal distance between those samples". Readings: forward differences, central differences, Horn/Sobel 3×3, Zevenbergen–Thorne. **Central differences (one-sided at the image edge); spacing = metres per pixel.** The normal is (−f·∂z/∂x, −f·∂z/∂y, 1) normalised; the sun vector is (sin az·cos el, cos az·cos el, sin el) in east/north/up, with azimuth clockwise from north (as stated).
55. **N-HSINPUT** — which value is "the elevation" isn't said (the `singleChannel` value or a named field). **The resolved `singleChannel` value.** Defaults for `factor` and `sun` aren't given: **factor 1, azimuth 315°, elevation 45°** (not used by the cases).
56. With a Symbolizer `colorMap` and a HillShading without `colorMap`: **the shade multiplies the colour from the Symbolizer colorMap** (as the case comment says). With a HillShading `colorMap`: **it replaces the colour.** With a HillShading `opacityMap`: **it multiplies the alpha** (replace vs multiply is open; not used).
57. **N-MAPINTERP** — /req/coverage/color-map and /rec/coverage/map-interpolation; NOTE: "The interpolation method is not specified". The colour space isn't stated either (sRGB vs linear vs Lab). **Linear in sRGB components; entries sorted by value; clamped outside.**
58. **N-ALPHACOMBINE** — how `alphaChannel` and `opacityMap` combine when both are set isn't stated. **Multiplied** (alphaChannel defaults to 1, so only the opacityMap counts in the cases). Then × Symbolizer `opacity`.
59. **N-NODATA** — NODATA cells aren't mentioned. **Transparent.** The grids here contain none.
60. Schema contradictions for coverages (JSON):
    - `singleChannel` is typed `zeroToOne`, but the cases (and clause 9) use elevations in metres.
    - The test styles write colours as `"#8a7a5a"`, but the schema's `color` allows only an object, array, web-colour name or expression, not a hex string. **Hex strings accepted.**
    - The ValueOpacity table repeats `color` ("Color associated with this value") instead of `opacity`, and both tables say `name` where the UML says `label`.
    - Default `colorChannels` = fields[0..2] "unscaled while colorChannels is 0 to 1" (TODO #150); not used.
61. Colours (N-COLNAMES): the Color class gives r/g/b as "float" with no range. JSON uses 0–255 for `color` and 0–1 for `color0to1` (`colorChannels`). The values of the named colours exist only in the CSS clause's table; the JSON schema only lists the names. **The clause 17 table is used for JSON too.**

## I. Not exercised / out of scope

Visualization passes and feature passes (`viz.pass`, `feature.pass`) are resolved (`viz.pass` = 0), but there is only one pass. `$include` is implemented but not exercised. Variables, functions beyond basic text/arithmetic, spatial/temporal predicates, and per-cell coverage selectors that differ between cells are not implemented. No case needs them.
